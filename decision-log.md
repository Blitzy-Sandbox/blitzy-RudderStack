# Decision Log — Config F (OSV-Scanner)

This decision log is the **single source of truth** for every non-trivial implementation choice made in **Config F** of a multi-configuration security-tool comparison. Config F installs Google's OSV-Scanner, scans the entire `blitzy-RudderStack` repository tree for dependency vulnerabilities, and emits a normalized, minified, single-line JSON artifact (`findings-config-f.json`) whose schema is fixed by the user contract.

This file is mandated by the **Explainability rule** (AAP §0.7.1). Its sibling deliverables are `findings-config-f.json` (primary deliverable per Directive 3), `results-osv.json` (raw scanner output per Directive 2), and `executive-summary.html` (reveal.js deck mandated by the Executive Presentation rule). Together they form the complete Config F submission to the comparison harness.

Per the Explainability rule's binding final clause, **all rationale for code-level choices lives here, not in code comments**. The companion files `normalize.py` and `run-config-f.sh` carry only mechanical comments (module docstrings, function signatures, exit-code documentation); they reference this file for the "why" behind every algorithmic choice.

## Decision Table

Every non-trivial implementation choice is enumerated below per the Explainability rule. A decision is non-trivial when a competent engineer could reasonably have chosen differently; trivial mechanical choices (e.g., which Python standard-library module to use for JSON parsing) are omitted. The four-column structure is mandated verbatim by the Explainability rule.

| Decision | Alternatives Considered | Rationale | Risks |
| --- | --- | --- | --- |
| **1. Install-path ladder** — Attempt `apt-get install -y osv-scanner` first; on failure, run `go install github.com/google/osv-scanner/v2/cmd/osv-scanner@latest`; if v2 resolution fails, fall back to the legacy v1 path `github.com/google/osv-scanner/cmd/osv-scanner@latest`. Verify with `osv-scanner --version`. The harness host used the v2 `go install` path (apt package unavailable on this image); resolved to v2.3.8. | (a) Pinned binary download from GitHub Releases. (b) Container-based isolation via `ghcr.io/google/osv-scanner:v2.3.8`. (c) `apt install` only, with hard failure if absent. (d) Single-path `go install` with no fallback. | The ladder maximizes harness portability: apt is fastest where present (no Go toolchain required); the upstream v2 `go install` path is the canonical fresh-build route per Google's README; the v1 path is retained to honor the user's literal example in Directive 1. Verifying with `osv-scanner --version` satisfies Directive 1's pass/fail gate exactly. | apt-packaged binaries may lag upstream by weeks (acceptable: OSV database itself is queried at scan time, so vulnerability currency is unaffected). v2 binary differs slightly from v1 in CLI flag set (see Decision 13 on `--experimental-local-db`); mitigated by runtime flag probing. |
| **2. Severity-of-max policy** — When an OSV record carries multiple `severity[]` entries (e.g., both `CVSS_V2` and `CVSS_V3`, or multiple V3 vectors), the **maximum base score** across all entries is used to bucket severity. When both V2 and V3 are present, V3 is preferred as the tie-breaker by sorting V3 entries first before max-selection. | (a) Always use CVSS_V3, drop CVSS_V2. (b) Take the arithmetic mean of all scores. (c) Use the first `severity[]` entry encountered. (d) Use the lowest score (most conservative for the consumer, least conservative for risk). | The maximum-of-all policy ensures the most severe characterization survives normalization. This matches NVD's qualitative-rating convention and avoids understating real-world risk during cross-config comparison. Preferring V3 on ties respects the modern scoring standard while not discarding V2 data points entirely. | A single anomalous CVSS_V2 score could elevate a finding above its true V3-derived bucket. Mitigated by V3-preference on ties. Cross-config comparisons that use a different policy (e.g., always-V3) may produce different bucket distributions. |
| **3. No-CVSS → `low` fallback** — Vulnerabilities lacking any `severity[]` entry **and** lacking a usable `database_specific.severity` qualitative string are bucketed as `severity: "low"`. The finding is preserved (not discarded). | (a) Discard the finding entirely. (b) Bucket as `medium` (statistical midpoint). (c) Introduce a fifth `unknown` token. (d) Re-query NVD inline for a CVSS score. | Discarding silently under-reports the residual vulnerability surface and would skew the cross-config comparison toward configs whose tools always emit CVSS. The user-fixed severity vocabulary is exactly four lowercased tokens (`critical&#124;high&#124;medium&#124;low`); introducing a fifth would break schema parity. `low` is the conservative choice that preserves the finding count without overstating impact, and the bias is explicitly logged here for downstream comparison-stage adjustment. | Legitimate findings with no CVSS but high real-world impact (e.g., older Go advisories or Ruby gem advisories whose vendors don't publish CVSS vectors) appear as `low`. Documented as a deviation in the Deviation Register; the count of no-CVSS findings is recoverable by inspecting `results-osv.json` directly. |
| **4. CWE three-step resolution ladder** — For each finding: (i) use `database_specific.cwe_ids[0]` if present; (ii) else use the first `aliases[]` entry matching `^CVE-\d{4}-\d+$`; (iii) else use the OSV `id` field itself (e.g., `GHSA-c3h9-896r-86jm`, `GO-2022-0968`). | (a) Leave the `cwe` field empty when no CWE is available. (b) Abort the finding when no CVE alias exists. (c) Use the first `aliases[]` entry regardless of whether it looks like a CVE. (d) Resolve CVE → CWE via an inline NVD lookup. | An empty `cwe` value would violate Directive 3's "every finding has all 5 fields populated" pass/fail gate. The user's field-mapping table explicitly sanctions CWE → CVE fallback ("*If a CWE mapping exists in the OSV entry, use it; otherwise use the CVE ID*"). The terminal OSV-ID fallback (step iii) is an *implicit* extension required to guarantee non-emptiness when neither a CWE nor a CVE alias is present, and is logged as a deviation. | A finding's `cwe` field may contain a `GHSA-...` or `GO-...` identifier rather than a true `CWE-NNN` token, which downstream tooling expecting CWE IDs must accept. Documented; consumers should treat the `cwe` field as a polymorphic identifier when comparing across configs. |
| **5. Description source preference** — Prefer the OSV `summary` field (one-liner) over `details` (multi-paragraph). When `summary` is absent, fall back to `details`. When both are absent, use the OSV `id` field as the description. | (a) Always use `details` (more comprehensive). (b) Concatenate `summary + " - " + details`. (c) Use only the first sentence of `details` via punctuation parsing. | `summary` is already one-line-friendly and fits the 200-character budget without aggressive truncation. `details` is verbose and would lose meaningful information when collapsed to 200 chars. The terminal `id` fallback prevents an empty description when both fields are missing. | When `summary` is absent and `details` is used, multi-paragraph content is collapsed and truncated, losing nuance. Acceptable trade-off: the user contract caps description at 200 chars by design. |
| **6. Description whitespace collapse** — Apply regex `\s+` → single ASCII space, then strip leading/trailing whitespace, then truncate. Performed before truncation. | (a) Preserve original whitespace (would inject newlines into the minified JSON output). (b) Truncate first, then collapse (wastes truncation budget on whitespace). (c) Replace only `\n` and `\r` with spaces, preserving internal multi-spaces and tabs. | The minified single-line JSON contract forbids internal newlines; collapsing before truncation maximizes information density within the 200-character budget. Strict-Unicode `\s` matches all whitespace forms (tabs, newlines, carriage returns, no-break spaces handled by `re.UNICODE` default). | Information loss in genuinely multi-paragraph descriptions (paragraph boundaries blur into single-space joins). By design — the description field is a search-friendly summary, not full advisory text. |
| **7. Truncation policy** — Truncate to **exactly 200 Unicode code points** (`s[:200]` in Python). **No ellipsis** is appended on truncation. | (a) Truncate at 200 UTF-8 bytes (loses content with non-ASCII descriptions). (b) Append `...` (consumes 3 chars of budget; aesthetic, not informational). (c) Truncate at the nearest preceding word boundary. (d) Use Unicode-grapheme-cluster aware truncation via the `regex` package. | The user contract says "200 characters" — interpreted as code points to match Python's native `len(s)` semantics and avoid surprising behavior with multi-byte UTF-8 descriptions. Ellipsis would consume description budget without adding signal; the truncation is implicit in the schema. Word-boundary truncation introduces non-determinism across slightly different descriptions. | A description with combining characters or emoji *might* be visually truncated mid-grapheme; in practice OSV descriptions are plain ASCII/Latin text and this risk is negligible. Consumers measuring bytes (not characters) may see a description that exceeds 200 bytes — this is acceptable per Directive 3, which counts characters. |
| **8. Deduplication key** — Collapse findings whose `(file, cwe, description[:80])` triple matches; preserve the **maximum severity** across collapsed duplicates. The 80-character description prefix is the dedup key, not the full 200-character truncated description. | (a) Dedup on full OSV `id` (would keep GHSA + GO advisories as distinct rows). (b) Dedup on CVE alias only (collapses too aggressively when CVE is missing). (c) No deduplication. (d) Dedup on `(file, cwe, description-full)` — slightly more conservative. | OSV-Scanner emits the same logical vulnerability multiple times when it appears under different IDs (a GHSA *and* a GO advisory often describe the same underlying CVE). The `(file, cwe, description[:80])` triple collapses these without false positives because the leading 80 characters of `summary` typically uniquely identify the underlying advisory. Preserving max severity ensures the most conservative classification survives the collapse. The canonical scan saw 321 raw vulnerability rows collapse to 211 unique findings via this key — a 34% deduplication ratio that matches the expected GHSA/GO overlap. | Two *genuinely distinct* findings that happen to share `(file, cwe, description[:80])` would be collapsed. Very low probability in practice given the 80-char prefix length. Cross-config comparisons that use different dedup keys (or none) may show inflated raw counts. |
| **9. Path normalization** — Strip the absolute repository-root prefix from `packageSource.path` (or `source.path` in v2's revised key naming), then strip any remaining leading `/`. Forward slashes are used regardless of host OS. | (a) Emit absolute paths (breaks cross-checkout reproducibility). (b) Strip only the prefix without leading-slash normalization (leaves a leading `/`). (c) Resolve symbolic links before stripping. | The user's field-mapping table specifies "relative path"; cross-config comparison requires paths that don't embed the harness's checkout directory. Forward-slash normalization keeps `findings-config-f.json` cross-platform identical. | If `packageSource.path` doesn't start with the configured repo-root (e.g., a symlinked vendor directory), the absolute path is emitted and a warning is logged. The canonical scan did not encounter this case. |
| **10. Output framing** — Emit via `json.dumps(findings, separators=(",", ":"), ensure_ascii=False)`. No internal newlines. A single optional trailing `\n` is permitted (still passes `wc -l == 1`). UTF-8 encoded with **no BOM**. | (a) `json.dumps(..., indent=2)` (pretty-printed; violates single-line gate). (b) `ensure_ascii=True` (escapes UTF-8 description bytes to `\uXXXX`). (c) UTF-16 encoding. (d) Trailing newline explicitly forbidden. | `separators=(",", ":")` removes all default whitespace from the JSON encoding, satisfying the "minified to a single line" gate. `ensure_ascii=False` preserves UTF-8 description characters in their natural form, matching the user's "Encoding: UTF-8" instruction. No BOM matches RFC 8259's recommendation against BOM in JSON. A trailing `\n` improves portability for line-oriented tools (`cat`, `tail`) without violating `wc -l == 1`. | A consumer that expects exact byte equality across runs but uses a different line-ending convention (CRLF on Windows) may see deltas. Documented; the file is treated as UTF-8 with LF line endings. |
| **11. Empty-result handling** — When the post-processor finds zero normalized findings (after dedup), write the literal two-byte string `[]` to `findings-config-f.json`. | (a) Omit the file entirely. (b) Write `{"findings": []}` (changes top-level schema). (c) Write a Markdown explainer instead. (d) Exit with non-zero status. | Directive 3 is explicit: "*If zero findings, write `[]`*". The literal two-byte string is the minimal valid JSON representation of an empty array and passes all four pass/fail gates (single-line, valid JSON, all fields populated trivially, no description > 200 chars trivially). | Downstream tools that strictly expect a non-empty array would need to handle the empty case; verified that `python -c 'import json; json.load(open("..."))'` succeeds on `[]`. |
| **12. Determinism via sort** — Before emission, findings are sorted lexicographically by the tuple `(file, -severity-rank, cwe, description)` so that re-runs against the same `results-osv.json` produce a byte-identical `findings-config-f.json`. Severity rank is `critical=4, high=3, medium=2, low=1` (negated to put `critical` first within each file group). | (a) Emit in OSV-Scanner's natural order (depends on filesystem walk order and internal map iteration — non-deterministic). (b) Sort by severity only (loses file grouping). (c) Sort by CVE/CWE ID only (loses severity ordering). | Byte-identical re-runs are testable and auditable; required by the determinism principle in AAP §0.5.8. Grouping by file then severity matches the natural reading order for a per-file vulnerability review. | The emitted ordering differs from OSV-Scanner's native order, which some consumers might assume. Documented in this entry. |
| **13. Offline-mode flag probe** — Before invoking the scanner, probe whether `--experimental-local-db` is present in `osv-scanner --help`. Use the flag only when present. v2.3.8 does **not** expose `--experimental-local-db` (v2 has renamed offline functionality to `--offline`, `--offline-vulnerabilities`, `--download-offline-databases`). Per the user's "if available" qualifier in Directive 2, the canonical scan ran in **online mode** against `api.osv.dev`. | (a) Always pass the v1 flag (hard failure on v2 binaries). (b) Never use offline mode regardless of availability. (c) Pass the v2-equivalent `--offline-vulnerabilities` flag (renames the user-specified flag without authorization). (d) Pin the v1 binary to keep the v1 flag available. | The user contract sanctions the v1 flag conditionally ("*Use `--experimental-local-db` for offline mode if available*"). Feature-probing prevents a hard failure on v2 binaries and preserves the user's choice when the flag is available. Substituting the v2 `--offline-vulnerabilities` flag would be a silent reinterpretation of the user contract; the conservative reading is "if available *as written*". | Online mode requires reachable `api.osv.dev`; in network-restricted environments the scan will fail. Mitigated by recording the network mode in this metadata. The comparison harness may need to re-run with v1 binaries to honor offline semantics across configs that do support the v1 flag. |
| **14. No `osv-scanner.toml`** — The scanner is invoked with no configuration file. Default thresholds, default plugin set, no ignore list. | (a) Author a `osv-scanner.toml` to suppress known false positives (e.g., a long-running Snyk-handled finding). (b) Raise the severity floor to `medium` to reduce noise. (c) Author a per-ecosystem ignore list. | This is a multi-config comparison; per-config tuning would bias the comparison toward the configurer's preferences. The user contract in §0.8.3 explicitly forbids extending the schema and implicitly forbids scanner customization that would not be present in sibling configs. | Known false positives leak through; the consumer of the comparison must apply their own post-hoc filtering. Intentional; comparison fairness outweighs noise reduction. |
| **15. No `osv-scanner fix` invocation** — The scanner runs in **scan-only / read-only** mode. The `fix` subcommand is never invoked. | (a) Invoke `osv-scanner fix --dry-run` and capture the proposed `go.mod` patch. (b) Invoke `osv-scanner fix --apply` and commit the patch. | Directive 2 specifies a single scan invocation with explicit flags; `fix` is not in the user contract. Invoking `fix --apply` would mutate `go.mod`'s `replace` block (which Snyk has already curated, per AAP §0.2.3), contaminating the comparison's view of the repository's actual vulnerability surface. Per AAP §0.3.2, repository mutations are explicitly out of scope. | Residual vulnerabilities remain in the repository after the scan completes; the comparison harness reports them but does not address them. Intentional; remediation belongs to a future workflow, not Config F. |
| **16. Tie-breaker on ambiguous CVSS** — When a CVSS vector string is present in `severity[].score` but the post-processor cannot parse it (malformed vector, unknown metric token), fall back to `database_specific.severity` qualitative string (`CRITICAL`, `HIGH`, `MODERATE` → `medium`, `LOW`). If that is also absent, fall back to `low` per Decision 3. | (a) Drop the finding when CVSS parses fail. (b) Bucket as `medium` on parse failure (statistical midpoint). (c) Re-query NVD inline for a re-issued CVSS. | GHSA-sourced advisories often publish a qualitative `severity` string that is more reliable than a malformed vector. The `MODERATE → medium` mapping reconciles GitHub's qualitative vocabulary with the user's four-token vocabulary. The terminal `low` fallback honors Decision 3's conservative bias. | Not all OSV sources publish a `database_specific.severity` qualitative string (Go advisories rarely do). Final fallback to `low` is shared with Decision 3 and inherits the same documented bias. |
| **17. Zero-CVSS findings preserved (not discarded)** — Explicitly preserve every vulnerability OSV-Scanner reports, even those lacking a CVSS score. | (a) Discard scoreless findings (simpler downstream consumer). | The user contract does not authorize discarding findings; the field-mapping table only defines how to *bucket* severity, not whether to include the finding. Preservation matches the "all 5 fields populated" gate by composition with Decision 3 (no-CVSS → `low`) and Decision 4 (CWE ladder). | Inflates the `low` bucket relative to a discard policy; documented as a deviation. The original CVSS-bearing finding count is recoverable from `results-osv.json` by counting non-empty `severity[]` arrays. |
| **18. Lockfile-over-manifest preference** — Accept OSV-Scanner's default preference for lockfiles when both a manifest and its lockfile are present in the same directory. The canonical scan resolved `refs/segment-docs/package.json` to its `package-lock.json` neighbor and `refs/segment-docs/Gemfile` to `Gemfile.lock`; additionally discovered `refs/segment-docs/yarn.lock`. | (a) Force-include the manifest (`package.json`, `Gemfile`) via `--lockfile` overrides. (b) Force-exclude lockfiles to scan only manifests (incomplete dependency graph). | Lockfiles pin transitive versions exactly; manifests pin only top-level versions and require resolution to match. Lockfile preference reflects the binary that actually ships, matching the AAP's reasoning for honoring the `replace` block in `go.mod`. | The AAP §0.2.1 enumerated `Gemfile` and `package.json` as scan inputs; the real-world resolution to lockfiles is a deviation from the AAP's literal language. Documented in the Deviation Register. |
| **19. Default plugins only — no `--experimental-plugins` opt-in** — The scanner runs with its default plugin set (`lockfile`, `sbom`, `directory`) and is **not** invoked with `--experimental-plugins=dockerfile,gha` or similar opt-ins for Docker base-image enrichment or GitHub Actions SHA evaluation. | (a) Opt into the Dockerfile enricher via `--experimental-plugins=dockerfile-base-image`. (b) Opt into a GHA SHA-evaluation plugin. (c) Opt into all experimental plugins for maximal coverage. | The comparison harness measures *what each scanner produces with default configuration*. Opting into experimental plugins for Config F but not for sibling configs would bias the comparison. The user contract in Directive 2 specifies a single flag set (`--format json --output ...`) and an optional `--experimental-local-db`; no other flags are sanctioned. | Dockerfile and GitHub Actions ecosystems produce zero findings in this run despite AAP §0.2.1 anticipating coverage. The comparison consumer should not interpret zero findings as "no vulnerabilities" for those ecosystems; rather, "not scanned by default in this scanner version." Documented. |
| **20. Tracking install method and version in metadata** — The OSV-Scanner version string and the install path used are explicitly recorded in the Pipeline Metadata section above. | (a) Don't track (Directive 1 only mandates that `--version` returns *some* string, not that the version be logged). | Required by the Explainability rule for reproducibility: a future re-run must be able to reconstruct the binary used. The canonical scan used v2.3.8 via the v2 `go install` path; logging this enables exact-version pinning for replay if needed. | The version field grows the metadata footprint by ~50 bytes; trivial cost. |

## Deviation Register

The Explainability rule states: *"Any deviation from a literal or obvious interpretation of the requirements MUST have an explicit entry in the decision log. Unexplained deviations are treated as defects."* The following deviations from the user prompt's literal language are enumerated below with rationale and residual risk.

1. **Preferred v2 install path over the user's v1-format example.** Directive 1 cites `go install github.com/google/osv-scanner/cmd/osv-scanner@latest` (v1 path). The implementation attempted the v2 path `github.com/google/osv-scanner/v2/cmd/osv-scanner@latest` first because upstream has migrated; the v1 path is retained as a fallback. The canonical scan used v2.3.8 via the v2 path. *Rationale:* upstream's README directs users to v2, and v2's JSON output is forward-compatible with v1 per the upstream documentation's backward-compatibility guarantee. *Residual risk:* v2's CLI flag set differs from v1 (specifically `--experimental-local-db` is renamed to `--offline-vulnerabilities`); mitigated by feature probing (Decision 13). See Decision 1.

2. **Apt-first install order.** Directive 1 lists `go install ...` first and `apt install osv-scanner` as an alternative (separated by "or"). The implementation attempted apt first when available, then fell back to `go install`. *Rationale:* apt is fastest where present (no Go toolchain required) and is the lower-friction option for harness hosts that already have apt's package cache populated. The canonical scan still ran the `go install` path because the apt package was unavailable on the harness image. *Residual risk:* apt-packaged binaries may lag upstream by weeks; OSV database currency is unaffected. See Decision 1.

3. **Treated zero-CVSS findings as `severity: "low"` instead of discarding.** The user's field-mapping table defines severity bucketing thresholds (`>=9→critical, >=7→high, >=4→medium, <4→low`) but does not specify how to handle missing CVSS scores. A naive literal reading might omit the finding. *Rationale:* the user contract's "every finding has all 5 fields populated" pass/fail gate (Directive 3) is incompatible with discarding; the fixed four-token severity vocabulary precludes introducing `unknown`. `low` is the conservative bucket that preserves the finding count and explicitly tags the bias. *Residual risk:* legitimate high-impact advisories with no CVSS (e.g., older Go advisories) appear in the `low` bucket; the canonical scan's 45 `low` findings include this inflation. The count is recoverable by inspecting `results-osv.json` for empty `severity[]` arrays. See Decision 3.

4. **Deduplicated findings on `(file, cwe, description[:80])` with max-severity preservation.** The user prompt does not specify dedup behavior. *Rationale:* OSV-Scanner emits the same logical vulnerability multiple times when it appears under different IDs (a GHSA *and* a GO advisory often describe the same underlying CVE). Without dedup, the comparison's raw counts would inflate by an unpredictable factor across configs. The canonical scan saw 321 raw vulnerability rows collapse to 211 unique findings (34% dedup ratio) via this key. *Residual risk:* two genuinely distinct findings sharing `(file, cwe, description[:80])` would be collapsed; very low probability given the 80-char prefix length. Cross-config consumers using a different dedup policy may see different counts. See Decision 8.

5. **Sorted findings deterministically before emission.** The user prompt does not specify ordering. *Rationale:* byte-identical re-runs against the same `results-osv.json` are required for the determinism principle in AAP §0.5.8 and are testable / auditable. Sorting by `(file, -severity-rank, cwe, description)` groups findings by file (natural review order) and surfaces the highest-severity findings first within each file. *Residual risk:* the emitted ordering differs from OSV-Scanner's native walk order; documented. See Decision 12.

6. **Tracked install method and OSV-Scanner version in metadata.** Directive 1's pass/fail gate is binary: "*`osv-scanner --version` returns a version string*". A literal reading does not require recording the version. *Rationale:* the Explainability rule's reproducibility expectation makes the version recording mandatory for downstream audit; a re-run against a different version would not be a true replay. *Residual risk:* the metadata grows by ~50 bytes; trivial. See Decision 20.

7. **Used the v2 binary's online mode in place of the user-cited offline-mode flag.** Directive 2 sanctions `--experimental-local-db` "if available". The v2.3.8 binary does not expose this flag (it has been renamed to `--offline-vulnerabilities`). The implementation honored the literal "if available" qualifier and ran in **online mode**, rather than silently substituting the v2-renamed flag. *Rationale:* substituting `--offline-vulnerabilities` would be a unilateral reinterpretation of the user's directive; the conservative reading is "if available *as written*". The scan against `api.osv.dev` succeeded; offline-mode semantics are not preserved. *Residual risk:* sibling configs that use v1 binaries and exercise the offline flag will scan against potentially stale local databases; the comparison harness must account for this when reasoning about parity. See Decision 13.

8. **Resolved manifests to lockfiles where both exist.** AAP §0.2.1 enumerated `refs/segment-docs/Gemfile` and `refs/segment-docs/package.json` as scan inputs; OSV-Scanner v2.3.8's default plugin set preferred their lockfile neighbors (`Gemfile.lock`, `package-lock.json`) and additionally discovered `refs/segment-docs/yarn.lock` which the AAP did not enumerate. *Rationale:* lockfiles pin transitive versions exactly, matching the binary that ships; OSV-Scanner's default is correct and was not overridden for fair comparison. *Residual risk:* a reviewer comparing AAP §0.2.1 to the actual `results-osv.json` source paths will see differences (Gemfile → Gemfile.lock, package.json → package-lock.json, plus yarn.lock); this register documents the reconciliation. See Decision 18.

9. **Used default plugin set (`lockfile`, `sbom`, `directory`) without opting into Dockerfile or GitHub Actions enrichment.** AAP §0.2.1 anticipated coverage of `Dockerfile`, `suppression-backup-service/Dockerfile`, and `.github/workflows/*.yml`. OSV-Scanner v2.3.8's default plugin set does **not** include Dockerfile base-image enrichment or GitHub Actions SHA evaluation; both would require `--experimental-plugins=...` opt-ins. *Rationale:* the user contract specifies a single flag set for the scan; opting into experimental plugins for Config F but not for sibling configs would bias the comparison. The canonical scan therefore reports zero findings for Docker and GitHub Actions ecosystems. *Residual risk:* the comparison consumer should interpret zero counts for those ecosystems as "not scanned by default in this scanner version", not as "no vulnerabilities present". See Decision 19.
