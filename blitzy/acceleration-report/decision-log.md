# Decision Log — Acceleration Measurement Deliverable

This is the canonical decision log for the `blitzy/acceleration-report/` measurement deliverable, produced per the Explainability rule (Agent Action Plan §0.7.1.3). Every non-trivial implementation decision — defined as one a competent engineer could reasonably have chosen differently — is recorded below with its alternatives, rationale, and residual risk. Per the rule, rationale lives ONLY in this file: code comments in the extraction scripts deliberately do not contain rationale, and reviewers should consult this log rather than inferring intent from script bodies. The decision table in §1 is paired with the Bidirectional Traceability Matrix in §2, which maps each of the twelve user-specified metrics to its extraction strategy, raw data artifact, compute function, and rendered locations in [`acceleration-report.md`](./acceleration-report.md) §6 Requirements Traceability Matrix and §11 Reproducibility Appendix.

## 3. Suggested Next Investigations

The following improvements were identified during preparation of this deliverable but are out of scope for the current measurement run. They are recorded here per the Onboarding & Continued Development rule (AAP §0.7.1.2) so a future analyst or maintainer can pick them up without rediscovering the rationale. Each item names the metric or rule it would strengthen, the access or capability it requires, and the resulting confidence improvement.

- **Linear API integration when a token is provisioned.** Once `LINEAR_API_KEY` is available in the analysis environment, re-running `make all` lifts Metric 6 (Flow Distribution) confidence to High by resolving the majority of PRs via issue labels rather than conventional-commit prefix, and produces a real value for Metric 12 (Defects Out of SLA) by reading severity tiers and SLA targets directly from Linear. The `scripts/08_extract_linear.py` script is a no-op when the key is absent, so no code change is required — only the environment variable.
- **Admin audit-log access.** A repo-admin GitHub token would let Metric 10 (Approved Exceptions) capture required-review bypasses, branch-protection rule modifications, and merges with failing required CI checks via the `/repos/{owner}/{repo}/audit-log` endpoint. This would lift M10 confidence from Low to High and remove the standing caveat required by `DL-008`.
- **JUnit XML emission in `tests.yaml`.** Adding `--junitfile junit.xml` to the `gotestsum` invocations in `.github/workflows/tests.yaml` would produce a stable test-result artifact on every CI run, lifting Metric 11 (Escaped Defects) from a HEAD-only snapshot to a transition-aware metric capable of detecting pass→fail and pass→skip events across `main`. This is a one-line workflow change in the analyzed repository and is therefore out of scope per `DL-001` but worth proposing in a separate change request.
- **Conventional-commit scope catalogue.** The repository already defines conventional-commit scopes (`core`, `gateway`, `jobsdb`, `warehouse`, `processor`, `router`, `batchrouter`, `destination`, and others) — these are not currently used by the Metric 6 classifier. A future enhancement to `compute_m6_flow_distribution()` could classify PRs by scope as well as by type, producing a richer per-actor distribution breakdown. The current first-success classifier order in `DL-009` would be extended to include a scope-aware tier between conventional-prefix and keyword-match.
- **Module attribution via Go AST.** The current majority-of-file-paths approach in `DL-011` could be replaced with package-graph analysis (`go list ./...`) for more accurate cross-package commit attribution, particularly for commits that touch generated mocks, proto definitions, or test helpers. The trade-off is a heavyweight Go toolchain dependency in the analysis environment, which is currently Python-only. A two-stage approach (path-majority by default, AST-based when a `--ast-attribution` flag is passed) would let the analyst opt in.
- **Window-alignment sensitivity analysis.** The current 2-week Monday-anchored window is hard-coded per the user definition. A future investigation could parameterise the window length (1-week, 4-week) and report sensitivity of each metric to the choice. This would surface metrics whose values are an artifact of the window boundary rather than the underlying signal.
- **Cross-repository comparison framework.** The current deliverable analyses a single repository. A future enhancement could parameterise the `GITHUB_REPO_SLUG` variable to accept a list and produce a side-by-side comparison report across multiple Blitzy-modified repositories, with the same twelve metrics computed by the same `09_compute_metrics.py` function applied identically to each repository's data.
- **CP3 review walkthrough for library, schema, and extraction-script modifications (forward-tracked from `DL-016` and `DL-017`).** At CP3 (executable-script review scope), perform a dedicated walkthrough of [`scripts/lib/git.py`](./scripts/lib/git.py), [`scripts/lib/github.py`](./scripts/lib/github.py), the five JSON schemas under [`scripts/lib/schemas/`](./scripts/lib/schemas/), and the two extraction scripts updated for the CP2 data contract — [`scripts/00_environment.sh`](./scripts/00_environment.sh) and [`scripts/02_extract_commits.sh`](./scripts/02_extract_commits.sh). Validate: (a) library public APIs (function names, signatures, return types) remain unchanged from the CP1 contract surface; (b) every artifact under [`data/`](./data/) parses and validates cleanly under the schemas; (c) `bash -n` succeeds on every shell script and `python3 -m py_compile` succeeds on every Python module; (d) a live rerun of `00_environment.sh` produces an `environment.json` whose top-level fields and `commit_date_range` triple match the CP2 contract documented in `DL-017`, and a live rerun of `02_extract_commits.sh` produces a `commits.csv` whose header uses the CP2-contract column names (`commit_sha`, `author_date_iso`, `committer_date_iso`, `parent_shas`) with every date field normalised to UTC `Z`-form; (e) the `make verify` target exits zero with the live (rerun-produced) artifacts in place. This walkthrough is the CP3 forward-tracked obligation that justifies retaining the post-CP1 modifications at CP2 per `DL-016` and the extraction-script updates per `DL-017`.
- **Deck-and-report Mermaid divergence audit (forward-tracked from `DL-015`).** At any checkpoint that touches the executive deck or the report's diagram set, run a presence-check audit verifying every diagram concept named in [`acceleration-report.md`](./acceleration-report.md) also appears in [`executive-summary.html`](./executive-summary.html), and that each inline deck diagram still carries its `%% deck variant of diagrams/<name>.mmd — audience: executive` comment header. This is the divergence-mitigation control referenced by `DL-015` and should be part of any future renderer-modification PR.
