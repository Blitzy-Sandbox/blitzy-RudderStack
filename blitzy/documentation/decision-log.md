# Decision Log — Config I (SonarQube — blitzy-RudderStack)

This decision log captures every non-trivial design and implementation choice made for **Config I** of the multi-config security-tool comparison series — a one-shot **SonarQube Community Build** static-analysis scan against the `blitzy-RudderStack` Go monorepo. The pipeline runs entirely inside an **ephemeral Docker container** (no `-v` volume mount, no persistent state on host), emits a single-line UTF-8 minified JSON array at `findings-config-i.json` (workspace root) conforming to the five-field schema specified in Directive 5 of the user prompt, and tears the container down on both the success and failure paths. Per the Explainability rule, this document is the **single source of truth for "why" decisions**; no rationale is duplicated in code comments or in the co-located `executive-summary.html`.

## Decisions

The table below enumerates every non-trivial implementation choice for Config I. A decision is non-trivial if a competent engineer could reasonably have chosen differently. Each row commits to a specific choice and acknowledges the residual risk.

| Decision | Alternatives | Why this choice | Risks |
|---|---|---|---|
| Use SonarQube Community Build (image `sonarqube:community`) rather than Developer, Enterprise, Data Center editions, or SonarSource Cloud. | Developer edition (adds taint analysis, PR decoration); Enterprise edition (portfolio dashboards, governance); Data Center edition (high availability); SonarSource Cloud (managed SaaS). | User Directive 1 specifies `docker pull sonarqube:community` literally. Open-source comparison parity requires the free Community offering across every config in the series so findings are directly comparable. | Reduced security-rule depth versus Developer edition; no taint analysis, no PR decoration, no SAML SSO. Acceptable because this is a one-shot comparative scan, not a CI-integrated long-term deployment. |
| Pull `sonarqube:community` as the rolling monthly Community Build, NOT a pinned calendar version (e.g., `sonarqube:25.12.0.123456-community`) or `sha256` digest. | Pin to a specific calendar version; pin to an immutable digest; mirror the image into a private registry. | Preserves the user prompt verbatim; keeps analyzer rules current month-over-month so cross-config diffs reflect the latest rule set. | Non-reproducible scans across days as SonarSource ships rule updates; cross-config comparisons require same-day reference snapshots. Mitigated by recording the scan timestamp in this decision log alongside the findings. |
| Bind SonarQube to host port 9000 with `-p 9000:9000` per the user Directive 2. | Remap to `-p 9001:9000` or another free port to sidestep any potential MinIO conflict. | Directive 2 specifies `-p 9000:9000` literally. The `docker-compose.yml` MinIO service only binds 9000 under the `storage` Compose profile, which is **inactive** in the default `docker compose up` invocation; conflict is contingent on that profile being explicitly enabled with `--profile storage`. | Scan fails immediately with `bind: address already in use` if any other listener holds port 9000 at scan start. Operators MUST pre-verify with `docker ps \| grep 9000` before launching the SonarQube container. |
| Authenticate with `-Dsonar.login=admin -Dsonar.password=admin` for both the scanner call and the Web API export. | Issue a short-lived token via `POST /api/user_tokens/generate`; rotate the admin password to a generated secret; provision a service-account user. | Directive 3 specifies the literal credentials. The scan window is short (typically 5–20 minutes for the 714 MB Go codebase) and the ephemeral container is destroyed at end of run; token issuance would add an extra round-trip with no security benefit in this short-lived isolated context. | Any in-flight third party on `localhost:9000` could authenticate during the scan window; mitigated by container network isolation and the short lifetime. Not acceptable for long-running deployments; this is one-shot only. |
| Issue the Issues Search call with `&ps=500` and do NOT paginate (no `&p=2`, `&p=3`, …). | Loop `&p=N` until `paging.total` is exhausted; raise `ps` above 500 (the SonarQube API ceiling IS `ps=500`). | Directive 4 specifies `&ps=500` verbatim and does not request pagination. `ps=500` is the documented API maximum; this is the largest single page possible. | Repositories with more than 500 VULNERABILITY+BUG findings get truncated to the first 500 results. Mitigated by emitting a stderr warning when `total > 500`; full pagination support is deferred to a follow-up config (Config II onward). |
| Map SonarQube severities to normalized severities exactly as the user table prescribes: `BLOCKER → critical`, `CRITICAL → critical`, `MAJOR → high`, `MINOR → medium`, `INFO → low`. Unmapped values default to `low` with a stderr warning. | Collapse BLOCKER and CRITICAL into distinct buckets; promote MAJOR to critical for a stricter posture; collapse INFO into medium. | Directive 5's severity table mandates this exact dictionary. Cross-config parity requires identical mapping so downstream diffs operate on the same vocabulary across all tools in the comparison series. | Loses the distinction between BLOCKER (release-blocker) and CRITICAL (immediate fix) in the normalized output; downstream consumers must consult raw SonarQube data for finer granularity. |
| For each unique rule key in the issues response, call `GET /api/rules/show?key=<rule_key>` and harvest CWE numbers from `rule.securityStandards.CWE[]`. | Parse `issue.tags` directly (which only contains the marker string `"cwe"`, never a numeric CWE ID); skip CWE enrichment entirely. | SonarQube's Issues Search API does NOT expose CWE numbers on individual issues. The canonical structured location for CWE identifiers is `rule.securityStandards.CWE[]` on the rule definition. Without this enrichment, the `cwe` field in the five-field schema would always degrade to `"CWE-UNKNOWN"`. | N+1 API call pattern (one `/api/rules/show` per unique rule key); rate-limit and latency cost on rule sets with many unique rules. Mitigated by `sort -u` over the rule keys before the loop so each rule is fetched at most once. |
| When `rule.securityStandards.CWE[]` is empty, regex-parse `rule.htmlDesc` for `CWE-\d+` patterns and use the first match. | Emit `null`, error out on enrichment failure, or skip the finding entirely. | Directive 5 wording "Rule tags CWE ID. If absent, infer from rule description" mandates the fallback path. Without it, many rules that reference CWE in prose but not in structured `securityStandards` would have no CWE assignment. | False positives if `rule.htmlDesc` references CWE numbers as counter-examples rather than the actual mapping (e.g., a description saying "this is NOT CWE-79"). Accepted because the alternative (skipping enrichment) breaks the five-field contract. |
| Emit the literal string `"CWE-UNKNOWN"` for the `cwe` field when both `securityStandards.CWE[]` and the `htmlDesc` regex yield nothing. | Emit `null`, empty string `""`, or omit the `cwe` field. | The user contract requires every finding to have **all five fields populated**. A sentinel preserves type stability (`cwe` is always a string) and allows downstream consumers to filter or count UNKNOWN-CWE findings explicitly. | Downstream consumers must handle the sentinel as a non-numeric string and not attempt to parse digits from it. Documented in the schema description in `executive-summary.html` for stakeholder awareness. |
| Pass `-Dsonar.exclusions=**/mock_*.go,**/*.pb.go,**/mocks/**` to the scanner invocation. | No exclusions (scan everything); broader exclusion of `*_test.go`; exclusion of `/internal/`. | The existing `.deepsource.toml` declares `exclude_patterns = ["**/mock_*.go", "**/*.pb.go"]`, establishing the convention. Mirroring it reduces noise from generated mock and protocol buffer files, which are not maintained by hand and not appropriate targets for SAST findings. | Legitimate bugs in mock or proto files masked from the scanner. Accepted because mocks and proto files are generated artifacts; any defect there is upstream in the generator template, not in this repository. |
| Apply `gsub("\\s+";" ")` (collapse all whitespace runs to a single space) BEFORE truncating to 200 characters with `.[0:200]`. | Truncate raw `issue.message`; preserve embedded newlines and tabs; truncate first then strip control characters. | Embedded newlines or tabs would break the single-line JSON invariant `cat findings-config-i.json \| wc -l == 1`. Normalizing whitespace FIRST guarantees the 200-character boundary lands on clean content; doing it AFTER could leave a control character at character 200. | Long multi-line messages lose detail (the original `issue.message` may have meaningful indentation). Mitigated by surfacing the raw `issue.key` in operational logs so reviewers can look up the full message via the SonarQube UI. |
| Use `jq -c .` to produce the minified single-line JSON output; defensively wrap as `printf '%s' "$(jq -c . payload.json)" > findings-config-i.json` if a trailing newline is observed. | A `python -c "import json,sys; json.dump(json.load(sys.stdin), sys.stdout, separators=(',', ':'))"` one-liner; hand-rolled string concatenation; a `node` one-liner. | `jq -c` is the smallest dependency that produces deterministic compact JSON output and is available via apt on every Ubuntu LTS. The `printf '%s'` wrapper eliminates the trailing newline some older `jq` versions emit, ensuring `cat findings-config-i.json \| wc -l` returns `1`. | Some pre-1.5 `jq` versions emit a trailing newline that would push `wc -l` to `2`; the `printf` wrapper defensively strips it. |
| Wrap teardown in a `trap` on `EXIT` clause that runs `docker stop sonarqube-test 2>/dev/null` then `docker rm sonarqube-test 2>/dev/null`, each guarded with an OR-true fallback so the script does not abort on an already-removed container. | Only invoke teardown at the end of the happy path; use `--rm` flag (incompatible with `-d` plus the persistent server lifecycle requirement during the scan window). | Failure to tear down on poll-timeout, scanner non-zero exit, API error, or normalization failure would leak a long-lived listener on host port 9000. `trap EXIT` ensures idempotent teardown under success AND failure paths. | Trap fires twice if an explicit `docker stop && docker rm` also runs at end of the happy path; the redirection-plus-fallback pattern makes both invocations idempotent. |
| Do NOT bind-mount any volume (`/opt/sonarqube/data`, `/opt/sonarqube/extensions`, etc.). The H2 embedded database and Elasticsearch indices live entirely inside the container layer. | Bind-mount `/opt/sonarqube/data` to persist the H2 database between runs (enabling incremental analysis and rule customization persistence). | The user prompt explicitly tears down with `docker rm`, and the design intent is "no persistent state on host". Persisting state would contradict the comparison-series goal of identical clean-slate runs across configs. | Every run pays the cold-start cost (~30–90s) and re-downloads bundled rules. Acceptable because runs are infrequent and cold-start time is captured as a measured metric for cross-config comparison. |
| Treat a quality-gate failure (non-zero scanner exit due to `qualitygate.wait`) as an INFORMATIONAL signal, NOT a fatal error. The Issues API export and normalization still run; the gate result is logged separately. | Abort export on non-zero scanner exit; treat gate failure as fatal and emit no findings file. | The deliverable is a findings inventory; the gate result is a derivative metric that should not block the inventory from being written. A blocked export would degrade the cross-config comparison value. | A gate failure may surprise operators who expect `set -euo pipefail` to halt the pipeline. Documented in the Operational Caveats section below. |
| Declare `LC_ALL=C.UTF-8` at the driver-script top; rely on `jq`'s default UTF-8 output for the final file. | Explicit `iconv -t UTF-8` pass over the final file; locale-agnostic byte-level concatenation. | Directive 5 specifies `Encoding: UTF-8`. `jq` emits UTF-8 by default; declaring `LC_ALL` eliminates locale-dependent variation on non-standard hosts and makes the output byte-stable across executor environments. | Locale variation on hosts without `C.UTF-8` may produce non-UTF-8 output. Explicit `LC_ALL` declaration in the driver script eliminates the variation. |
| When `issues.length == 0`, write the literal two-byte sequence `[]` to `findings-config-i.json` (no whitespace, no trailing newline, no BOM). | Empty file; `null`; `{}`; `{"issues":[]}`; `{"findings":[]}`. | Directive 5 explicitly states "If zero findings, write `[]`". The contract is byte-stable across configs so downstream diffing tooling can distinguish `[]` (scan ran, no findings) from an absent file (scan failed mid-pipeline). | Downstream consumers must distinguish `[]` (scan succeeded with zero findings) from an absent file (scan failed mid-pipeline). The contract is documented here so reviewers understand the semantics. |
| Set `sonar.sources` to the repository root (the entire `blitzy-RudderStack` working tree) rather than listing specific Go package paths. | Pass only `cmd/`, `app/`, `gateway/`, `processor/`, etc., as a comma-separated list; restrict to a curated subset of the 1,263 `.go` files. | The repository is a single Go monorepo with one `go.mod`; scoping by package would risk missing cross-package vulnerabilities. The `sonar.exclusions` directive already prunes generated mocks and proto stubs, so over-inclusion is bounded. | Scan duration scales with input size; the full tree at ~714 MB takes longer than a scoped scan. Accepted because cross-config comparison requires consistent input coverage. |
| Polling sleep interval set to `sleep 2` between `/api/system/status` checks during the 120-second cold-start window. | `sleep 1` (more aggressive polling, more load); `sleep 5` (lighter polling, slower detection); exponential backoff. | A 2-second cadence yields up to ~60 status checks within the 120-second ceiling, balancing detection responsiveness against avoiding spurious load on the still-initializing SonarQube server. | A 2-second granularity may overshoot the actual UP transition by up to 2 seconds when reporting cold-start time. Accepted as adequate measurement precision for cross-config comparison. |
| Leave the existing `.deepsource.toml`, `.snyk` (Snyk SCA policy v1.22.1), and `.golangci.yml` (gosec, depguard, forbidigo, bodyclose) UNCHANGED. Reference the DeepSource exclusion convention; ignore Snyk SCA ignores (out of SonarQube SAST scope); accept gosec overlap with SonarQube's Go security rules. | Suppress findings already covered by gosec; merge `.snyk` ignores into SonarQube via custom rule profiles; rewrite `.deepsource.toml` to align with `sonar.exclusions`. | The comparison series goal is to surface where each tool independently agrees or disagrees on the same source corpus. Cross-tool policy harmonization is an explicit anti-goal for this snapshot config; downstream configs reconcile findings across tools. | Same finding reported by multiple tools (gosec + SonarQube + DeepSource) creates triage burden for the eventual remediation campaign; mitigated by the cross-config diff scripts planned for the comparison series rollup. |

## Deviations from Literal Interpretation

Per the Explainability rule's "Any deviation from a literal or obvious interpretation of the requirements MUST have an explicit entry in the decision log. Unexplained deviations are treated as defects" mandate, the following deviations from a literal reading of the user prompt are documented here with rationale and controlling source.

### Deviation 1: Scope expansion from 1 file to 3 files

- **Literal interpretation:** The user prompt header reads `[5 directives | ~0 files modified | 1 new file]`, suggesting only `findings-config-i.json` is to be created.
- **Actual implementation:** Three new files are created — `findings-config-i.json` (workspace root), `blitzy/documentation/decision-log.md` (this file), and `blitzy/documentation/executive-summary.html`.
- **Why the deviation:** Two user-specified rules — Explainability (AAP §0.7.1.1) and Executive Presentation (AAP §0.7.1.2) — MANDATE additional deliverables. The Explainability rule requires "Deliver a decision log as a Markdown table"; the Executive Presentation rule requires "Every deliverable MUST include an executive summary as a single self-contained reveal.js HTML file". Per the AAP framework's RULE-DRIVEN SCOPE principle, rule mandates expand the in-scope file set.
- **Controlling source:** User-specified rules in the prompt body, captured verbatim in AAP §0.7.1.

### Deviation 2: Inlined theme in `executive-summary.html`

- **Literal interpretation:** The Executive Presentation rule references a canonical theme file at `blitzy-deck/references/blitzy-reveal-theme.css`, implying that file should be imported by the presentation.
- **Actual implementation:** The full Blitzy reveal.js theme — all CSS custom properties (`--blitzy-primary`, `--blitzy-primary-dark`, the full set), slide-type classes (`slide-title`, `slide-divider`, `slide-closing`), and component classes (`kpi-card`, `kpi-grid`, `accent-bar`, etc.) — is INLINED directly into the `<style>` block of `executive-summary.html`.
- **Why the deviation:** The canonical theme file `blitzy-deck/references/blitzy-reveal-theme.css` does NOT exist in this repository (verified by directory-tree inspection during AAP §0.2 discovery). Per the rule's "Single self-contained HTML file, no build steps, no local file dependencies" requirement, inlining the theme is the only way to satisfy "self-contained" given the canonical file's absence.
- **Controlling source:** Executive Presentation rule in AAP §0.7.1.2.

### Deviation 3: No `sonar-project.properties` file created

- **Literal interpretation:** SonarQube conventionally uses a `sonar-project.properties` file at the project root to declare scan configuration; many tutorials show that convention as the default.
- **Actual implementation:** All scanner configuration flows through the six `-D` CLI flags specified in Directive 3. No properties file is created or committed to the repository.
- **Why the deviation:** Directive 3 specifies all six configuration values inline via `-D` flags. Creating a properties file would duplicate configuration and risk drift between the file and the user's verbatim invocation. AAP §0.8.1 explicitly mandates verbatim preservation of the user's commands; introducing a properties file would alter the invocation surface and is therefore disallowed.
- **Controlling source:** Directive 3 in the user prompt; AAP §0.8.1.

### Deviation 4: No CI workflow integration

- **Literal interpretation:** A common SonarQube integration pattern is a GitHub Actions workflow (`.github/workflows/sonarqube.yml`) that runs the scan on pull request or push events with SonarSource's `sonarqube-scan-action` or a custom Docker step.
- **Actual implementation:** The 13 existing workflows under `.github/workflows/` are NOT modified, and no new SonarQube workflow is created.
- **Why the deviation:** The user prompt scopes Config I to a one-shot local run. CI integration would require pipeline secrets management, runner configuration, ongoing operational responsibility, and SonarQube Server provisioning outside the scope of a comparison-series snapshot. CI integration is deferred to a downstream config in the series, if and when scheduled.
- **Controlling source:** AAP §0.3.2 (Explicitly Out of Scope).

## Operational Caveats

- **Pre-verify host port 9000 is free** before launching the SonarQube container: `docker ps \| grep 9000` should show no listener. The most common conflict source on this repository is MinIO under the `storage` Compose profile defined at lines 33–39 of `docker-compose.yml`, which only binds 9000 when `docker compose --profile storage up` is invoked. Default `docker compose up` does NOT start MinIO.
- **Confirm the Docker daemon is running** and the executing user is in the `docker` group: `docker info` should succeed without `permission denied` before any `docker pull` or `docker run` step.
- **Ensure ≥3 GB free disk** for the `sonarqube:community` image pull (~1.4 GB compressed, ~3–5 GB extracted on overlay2) plus ~500 MB headroom for the scanner cache at `~/.sonar/cache/`. The cache is host-side and persists across runs; this is acceptable because it stores only plugins and bundled rules, not findings data.
- **Confirm `apt install sonar-scanner` resolves** on the executor's package source. Ubuntu 24.04 LTS and 25.10 verified during setup; other Linux distributions may require adding SonarSource's apt repository or falling back to the manual ZIP install from the SonarSource download page.
- **Quality gate failure does NOT block the export** — operators reading non-zero exit codes from the scanner step should consult the gate-result log line in the driver-script stderr output, not assume the export is missing or corrupted. The Issues API export and normalization run regardless of gate status.
- **Pagination caveat** — if the Issues API response reports `paging.total > 500`, the output is truncated to the first 500 findings. The driver script surfaces this as a stderr warning. Full pagination support is deferred to follow-up configs (Config II onward); operators of this repository at this point in time should treat any truncation as a blocker and escalate.
- **No persistent SonarQube state** — every invocation incurs a fresh ~30–90s cold-start while Elasticsearch indices initialize inside the container. This is by design; operators should not bind-mount `/opt/sonarqube/data` to accelerate subsequent runs, because doing so would violate the comparison-series invariant of identical clean-slate environments across configs.
- **Operational scripts are NOT committed** — the driver script (`run-config-i.sh`, intermediate `issues.json`, per-rule `rules-*.json` enrichment payloads) is invoked on the executor host only; only the three deliverable artifacts (`findings-config-i.json`, this `decision-log.md`, `executive-summary.html`) are committed to the repository.
